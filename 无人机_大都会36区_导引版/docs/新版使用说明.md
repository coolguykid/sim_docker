# 第一版增强版使用说明

代码目录：`D:\无人机_大都会36区_第一版增强`。修改基准是 `D:\无人机_仅算法1`，原目录不修改。

## 启动与默认设置

在 PowerShell 中运行：

```powershell
Set-Location -LiteralPath 'D:\无人机_大都会36区_第一版增强'
D:\Anaconda3\envs\hxy2\python.exe -B main.py
```

仍使用原来的参数窗口和三维预览。默认是一个 30 km × 30 km、六层的大都会，先生成完整管道和匝道，再按地面正方形切成 6 × 6 个管理区域。每份底面为 5 km × 5 km，不会复制出 36 张独立路网。区域归属以管道、匝道中心线为准，车道宽度保留原来的真实偏移。

每层默认 50 根管道，每根 20 条车道，底层共有 1000 个入口槽位。六层限速依次为 19、40、60、80、100、120 m/s。转弯和进入较低限速段前会实际减速；目前用“在折线转角停稳后转向”表示转向，尚未建立飞机转弯半径和姿态模型。

中间节点默认数量为 0。每次仿真默认一次抽取第六层管道内部的 10 个终点，整次仿真所有批次共用；随机种子默认 42，实际终点写入结果文件。也可以选择每批重新抽取，或使用手动终点表指定管道、车道和准确位置。

修改管道数、车道数后，如果还要使用手动终点或中间节点，请先点击刷新预览，核对位置，避免把旧路网编号误用于新路网。

## 三种寻路方式

三种方式的区域间、区域内寻路都使用 Dijkstra。

| 面板选项对应代码值 | 路径由谁计算 | 无人机侧掌握的信息 |
|---|---|---|
| `centralized_full` | 服务器起飞前计算完整详细路线 | 已下发的完整路线 |
| `centralized_regional` | 服务器只计算当前区域的详细路线，进入新区域再计算 | 区域连接摘要、当前区域详细路线 |
| `onboard_regional` | Ray 工作进程中每架逻辑无人机自己的规划器计算当前区域路线 | 区域连接摘要、当前区域完整拓扑；进入新区替换旧区 |

完全分布式模式使用真实 Ray 进程。万架仿真按组运行，组内无人机各有自己的规划状态；没有创建一万个系统进程。服务器仍然集中检查安全，这是寻路分布式和避障集中式的组合。

本次机载小规模测试使用 **120 架、30 架/进程、4 个真实 Ray 工作进程**。原面板保留 300 架/进程；目标为一万架时会产生 34 个进程。进程数会影响 CPU 和内存需求，本次未完整验证机载万架性能或 34 进程的组合。

三种模式的中央避障还会额外计算完整参考航程并提前做全程安全预约，以防无人机在途中互相堵住。这个参考航程留在服务器，不下发未来区域地图给机载规划器。第二、三种模式进入新区时仍会实际重新计算本区路线，并在边界停稳后与安全预约核对；不一致时停止运行并报告错误。因此第三种模式不表示取消了中央服务器或全局安全预测的计算开销。

## 起飞与补机

开始时最多新增 1000 个任务。默认每 100 个物理秒检查一次，在飞和地面待放行任务的合计数量不足目标上限时补充，每次最多 1000 个。任务只有在入口及后续运动安全时才真正起飞。

“目标上限 10000”不等于每次仿真都能实际同时飞满 10000 架。飞得较快、补得较慢时，实际峰值会低一些。结果分别报告累计生成、实际起飞、到达、在飞、地面等待和在飞峰值。

配置的补机时段结束后停止新增，再用单独的排空时段等待已有任务完成。超过排空时限的任务保留为未完成，不计入到达。

## 0.1 秒和 1 秒

面板选择的是物理秒。补机、速度、加速度、匝道和到达时间使用同一套秒制，不再把“预测一秒”和“执行一回合”混在一起。

位置由连续的加速、匀速、减速轨迹计算；0.1 秒或 1 秒是输出和同步时间网格。穿过边界、起飞、停车和到达可以发生在两个网格点之间，剩余时间会继续处理。每段轨迹在安装前检查全过程的最近距离，证书有效期间复用检查结果，不只比较两个时刻的位置。

默认安全预约搜索至少按 0.1 个物理秒向后尝试放行时间，这个参数与输出步长分开，1 秒和 0.1 秒输出使用同一套放行逻辑。可选 Numba 仅加速相同的连续计算；没有安装时仍可使用 Python 参考实现。

不同高度的安全距离分别为 8、10、15、20、25、30 米。近邻空间索引只用来找候选，最终检查仍使用三维连续轨迹。轨迹被拒绝时先等待，必要时沿已选路线前进到安全排队位置再停下。

## 原面板功能

运力比例、可选中间节点、航迹选择、逐时隙日志、KL/通信指标、JSON 帧导出和旧空域模式继续保留。中间节点开启后，无人机先真正到达节点并停车，再继续飞向最终目标。

大都会中的动态匝道密度会改变道路数；这一增强模式在本次运行期间保持这些道路开启。低、中、高、超高对应有界配额，避免产生所有管道两两相连的大图。原数据库接入与旧空域运行代码仍在原模块中。

## 输出与 Unity／团结引擎接口

每次运行单独输出到 `artifacts/runs/<运行编号>/algorithm_1/`。`summary.json` 是统计，`arrivals.ndjson` 每行记录一架实际到达的无人机，`timing/turn_times.txt` 记录真实计算耗时。若勾选全量 JSON 导出，还会生成场景、帧和完成状态清单。

Python 接口已预留在原运行流程中：

```python
from uav_sim.simulation.metropolis_runtime import MetropolisSession

with MetropolisSession(env, config) as session:
    progress = session.advance_one_step()  # 按 config['sim_dt_seconds'] 前进一步
    if progress['failed']:
        raise RuntimeError(progress['failed'])
    frame = session.current_frame()
```

`current_frame()` 返回 JSON 可序列化的数据，含物理时间、时隙步长、单位米，以及无人机编号、三维坐标、速度、区域、管道、车道和目标位置。Unity 可以通过后续增加的 TCP、HTTP 或插件传输层读取这些数据；本版本提供计算和帧接口，没有附带 Unity 工程。若步长为 0.1 秒，需要计算下一秒时调用十次前进一步；步长为 1 秒时调用一次。

本程序的坐标顺序是 `(X, Y, Z)`，其中 `Z` 表示高度。接入端若用 `Y` 表示高度，可把位置统一映射为 `(X, Z, Y)`；道路、匝道、无人机和终点必须使用同一套转换，朝向和旋转由接入端另行约定。

接口抛出异常或返回 `failed` 时，接入端应停止推进并保留最后有效画面，不继续读取未来位置当作新帧。这里的停止是停止仿真计算，不是实机紧急停车指令。

高级 JSON 配置还提供 `stop_at_region_boundaries=false`：在固定路网、导航结果一致的情况下，直管道跨管理区可以连续通过，实际转弯仍减速。默认和正式验收保留更保守的边界停车策略；连续过区选项已另做小规模对照，不混入默认六组结果。

无界面复现实验也使用同一个应用入口：

```powershell
D:\Anaconda3\envs\hxy2\python.exe -B main.py --config configs\my_run.json
```

万架验收的具体配置、运行日志和实际结果另见测试报告。安全性与到达率应以这些记录为准，不能把小规模测试通过当成所有路网、所有负载下的到达保证。
