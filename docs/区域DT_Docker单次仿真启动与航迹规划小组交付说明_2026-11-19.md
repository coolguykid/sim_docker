# 区域 DT Docker 单次仿真启动与航迹规划小组交付说明

> 日期：2026-11-19  
> 项目目录：`sim_docker`  
> 适用范围：当前35区域 Docker 验证环境、交付版 `centralized_regional` 适配、严格事件跨区协调  
> 目标读者：航迹规划算法小组、区域 DT 框架开发人员

## 1. 当前 Docker 部署组成

当前 `compose.yaml` 启动：

- `region-dt-01` 至 `region-dt-35`：35个区域 DT 容器；
- `simulation-coordinator`：一个跨区域推演协调器容器。

每个区域容器内部同时运行：

- PostgreSQL/TimescaleDB 基础镜像中的 PostgreSQL；
- 当前区域的路网数据库；
- 区域 DT HTTP 服务；
- 区域仿真会话；
- 区域路径规划、运动推进和统计适配代码。

协调器只负责：

- 等待本次参与区域全部注册；
- 维护全局仿真逻辑时间；
- 执行严格事件 `prepare/commit` 屏障；
- 选择每一轮全局最早跨区事件；
- 转发跨区移交事件；
- 在整秒边界通知各区域输出帧；
- 汇总本次协调状态和计时。

协调器不负责：

- 从数据库加载路网和 UAV；
- 解释导引；
- 计算区域路径；
- 执行避碰和加减速；
- 判断拥堵；
- 调整路网；
- 下发最终导引。

## 2. 当前一次测试推演的实际输入

生产设计中的推演输入应当是：

```text
中心 DT 下发的导引 P
＋ 各区域数据库中的当前路网
＋ 各区域数据库中的 UAV 快照及最终目的信息
```

当前数据库还没有完整、可直接使用的 UAV 推演快照和最终目的信息，因此测试脚本临时完成以下工作：

1. 从35个区域容器的 `/api/v1/topology` 读取实际路网；
2. 将35个区域路网临时汇总为测试用全局 `PartitionGraph`；
3. 根据全局图中的合法边界转移生成均匀概率导引；
4. 随机生成 UAV 的源区域、源管道、目的区域和目的节点；
5. 按初始所属区域拆分 UAV；
6. 向35个区域的 `/api/v1/guidance` 分别提交同一个 run；
7. 等待协调器完成严格事件推进；
8. 汇总区域 CSV 和执行时间。

因此，当前测试中的以下内容是临时替代项：

| 生产输入 | 当前测试替代 |
|---|---|
| 中心 DT 汇总的全局图 | 测试脚本从35个区域接口临时汇总 |
| 中心 DT 下发的真实矩阵 P | 根据合法出口生成均匀概率 |
| 区域数据库 UAV 快照 | 测试脚本随机生成 |
| UAV 数据库目的信息 | 测试脚本随机生成目的区域和目的节点 |

## 3. 第一次启动前的环境要求

### 3.1 必需软件

- Windows 10/11；
- Docker Desktop，使用 Linux containers；
- Docker Compose v2，即 `docker compose` 命令；
- Python 3.10 或当前已经安装依赖的 `traffic` Conda 环境；
- 首次构建镜像时可访问 Python 包源和 Docker 镜像仓库。

### 3.2 建议资源

用于小规模功能验证，建议至少：

- 主机内存：16 GB；
- Docker Desktop 分配内存：8 GB以上；
- CPU：8个逻辑核心以上；
- 可用磁盘：20 GB以上。

10000架、900秒属于压力测试，资源需求和运行时间取决于跨区事件数量、安全控制复杂度和 CSV 输出量，不能用小规模冒烟测试时间直接推算。

## 4. 构建并启动全部容器

在 PowerShell 中进入解压后的项目目录：

```powershell
cd D:\shuo\sim_docker
```

首次启动或源码发生变化时：

```powershell
docker compose up -d --build
```

后续没有源码变化时：

```powershell
docker compose up -d
```

首次启动会进行：

1. 构建 `airway-region-dt:dev`；
2. 构建 `airway-simulation-coordinator:dev`；
3. 创建35个 PostgreSQL named volume；
4. 从 `region_data/region_001` 至 `region_035` 导入区域数据；
5. 启动35个区域 API；
6. 等待区域健康后启动协调器。

区域数据库已经有 `node_info` 数据时，导入脚本会跳过，不会重复插入路网。

## 6. 启动一次推荐的小规模仿真

`run_id` 必须唯一。测试脚本会创建 `test/runs/<run_id>`，已存在时不会覆盖。

使用当前 `traffic` 环境：

```powershell
C:\Users\coolguykid\anaconda3\envs\traffic\python.exe `
  test\run_random_35_complete_mode.py `
  --run-id planning_team_smoke_001 `
  --uavs 100 `
  --duration 10 `
  --departure-span 1 `
  --seed 20261119 `
  --timeout 600
```

如果对方使用普通 Python，并已安装依赖：

```powershell
python test\run_random_35_complete_mode.py `
  --run-id planning_team_smoke_001 `
  --uavs 100 `
  --duration 10 `
  --departure-span 1 `
  --seed 20261119 `
  --timeout 600
```

参数说明：

| 参数 | 含义 |
|---|---|
| `--run-id` | 本次推演唯一编号 |
| `--uavs` | 随机生成的 UAV 数量 |
| `--duration` | 仿真时长和输出帧数，当前 `dt=1s` |
| `--departure-span` | `spawn_turn` 的随机范围 |
| `--seed` | 随机任务种子 |
| `--timeout` | 宿主机等待整次推演完成的最大秒数 |
| `--submit-workers` | 并行向区域提交导引的宿主机线程数，默认8 |

该脚本使用的是当前严格事件协调器。一个1秒输出帧可能被分成多个事件子步，但各区域只在整秒边界写一次前端帧和交通统计。

- 当前尚未完成跨区域入境安全预留；

建议航迹规划小组先用100架、10秒确认环境和接口，再逐步提高规模。

## 10. 当前导引版接入方式

### 10.1 当前真正使用的内容

区域会话当前使用：

- 交付版 `RegionalRoutingBackend`；
- `routing_mode="centralized_regional"`；
- 交付版 `RegionalControl`；
- 交付版 `partition_motion.advance`；
- 数据库路网适配后的 `RoadNode/RoadEdge`；
- 区域 DT 自己实现的 Docker 会话、跨区移交和 CSV 统计。

外部导引通过：

```text
global_guidance_transfers
  → HybridPartitionMaps
  → 跨区域边附加代价
  → RegionalDijkstra
```

当前 HTTP 请求中的导引不是裸二进制矩阵，也不是 NumPy 对象，而是 JSON 中的稀疏合法转移列表：

```json
{
  "source_region_id": 1,
  "source_layer": 100,
  "target_region_id": 2,
  "target_layer": 100,
  "proportion": 0.5
}
```

这相当于只传输 P 中合法且非零的元素。

### 10.2 当前没有使用的原始完整运行链

当前区域 Docker 没有直接运行交付版：

```text
main.py
→ run_config()
→ run_simulation()
→ MetropolisSession.run()
→ CertifiedJourney.run()
```

原因是该链路会自行生成 UAV、内部计算导引，并将所有区域 UAV 保存在一个 `MetropolisSession` 中，与区域 Docker 的数据和所有权模型不同。

## 11. 接入导引版时遇到的主要问题

### 11.1 交付版导引来源与项目要求不同

交付版通过 `GuidanceModel` 根据仿真 UAV 分布自行计算 P；项目要求区域 DT 接收中心 DT 下发的 P。

当前适配绕过内部 `GuidanceModel`，直接把外部 P 的稀疏转移转换为边代价。这可以影响寻路，但不等于完整复用交付版导引运行链。

### 11.2 交付版强制导引只能使用 `certified_journey`

源码存在：

```python
if (guidance_config.enabled or guidance_config.evaluate) \
        and engine != "certified_journey":
    raise ValueError("guidance requires the certified_journey engine")
```

这限制的是交付版内部导引模块。外部 P 可以经适配器用于寻路，但交付版没有实现“外部 P＋`certified_prefix/per_step`＋安全证书”的完整组合。

### 11.3 `certified_journey` 需要完整全局安全信息

`certified_journey` 需要：

- 全局详细 `PartitionMaps`；
- 所有区域 UAV 的状态；
- 完整参考路径 `JourneyRoutes`；
- 完整连续未来轨迹；
- 全局 `PrefixReservations`；
- 每个任务的导引代价版本。

当前每个区域 Docker 只有本区域 UAV 和路网，协调器也不保存完整 UAV 帧或全局时空预留，因此区域 Docker 无法获得这些信息。

### 11.4 完整航程认证与严格滚动规划冲突

当前业务要求：

```text
进入下一区域后
→ 下一区域才开始规划本区域路径
```

`certified_journey` 则在起飞前预测完整参考航程。区域边界虽然会再次规划，但新规划必须与参考航程一致，否则抛出 `ReferenceMismatch`。

### 11.5 `centralized_regional` 不等于区域独立推进

交付源码中的 `centralized_regional` 只限制寻路返回当前区域前缀。原始仿真仍由一个 `MetropolisSession` 保存和推进全部 UAV，没有跨 Docker 所有权移交。

### 11.6 当前严格事件协调只解决时序

当前已经解决：

- 精确 crossing time；
- 同一秒剩余时间；
- 全区域事件顺序；
- 源区域删除和目标区域接收；
- UAV 不重复、不丢失。

尚未解决：

- UAV 进入目标区域前的安全预准入；
- portal 静止占用/HOLD；
- 目标区域入口轨迹预留；
- 目标区域拒绝时的源区域安全制动；
- 分布式安全证书和版本失效。

所以当前实现完成的是跨区时间正确性，不是完整跨区安全正确性。

### 11.7 当前全局图是测试替代

测试脚本从35个区域 Docker 实时读取并合成全局图。生产环境应由中心 DT 提供定期汇总的全局图，区域 Docker 不应自行访问其他区域数据库。

### 11.8 当前测试导引不是真实中心导引

`build_uniform_guidance()` 对每个 `(区域, 层)` 的合法出口采用均匀概率，只用于验证导引数据能够进入规划器。它没有验证中心 DT 的实际 P 格式、版本、发布时间和重发策略。

### 11.9 当前 UAV 快照是测试脚本生成

`generate_missions()` 随机生成源目，并为避免初始安全重叠限制为一个开放管道最多放置一架 UAV。生产环境必须从数据库加载真实 UAV，并获得最终目的区域/目的节点。

### 11.10 规划失败策略仍是测试策略

随机 OD 在某区域无法规划时，当前测试允许该 UAV 变为 `BLOCKED` 并留在规划起点。这是压力测试容错，不是最终业务策略。

## 12. 需要航迹规划小组共同确认的接口

建议航迹规划小组重点确认：

1. 是否接受 `centralized_regional` 作为区域 DT 的正式寻路方式；
2. 外部矩阵 P 如何输入，是否接受稀疏合法转移列表；
3. P 如何转换为路径代价；
4. `guidance_revision` 在一次推演中是否固定；
5. 区域规划结果是否只返回当前区域 `edge_ids`；
6. 如何明确返回出口 portal、目标区域和目标层；
7. 是否提供到 portal 的连续轨迹候选；
8. 跨区域安全采用完整航程认证、区域前缀预留，还是目标区域预准入；
9. 规划失败、版本不一致和路网变化时返回什么状态；
10. 哪些模块属于航迹规划算法交付，哪些属于区域 DT 框架协调。
