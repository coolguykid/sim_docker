交付日期：2026-11-19（北京时间）

## 1. 交付范围

本次将独立的《无人机_大都会36区_导引版》放入 `sim_docker/无人机_大都会36区_导引版/`。区域镜像继续从这个位置构建，数据库、区域 DT、协调器和导引算法可在同一个 Compose 工程内运行。

数据库种子和 Compose 服务覆盖区域 1–35。区域 36 出现在部分邻区声明中，但本次输入缺少其拓扑、设施状态和独立区域数据库。验收使用基于真实数据库的 `centralized_regional` 和固定外部导引，验证区域 1 到区域 2 的滚动寻路、移交和结果输出。

## 3. 数据与调用关系

1. 区域容器启动 PostgreSQL，执行 `initdb/001_schema_.sql`，再由 `region_image/import_region_data.sh` 导入原始区域 CSV。
2. `submit_guidance_demo.py` 作为临时中心 DT 客户端，通过 `GET /api/v1/topology` 读取指定区域的拓扑。它将数据库投影转换为适配器的字段格式，交给 `build_global_partition_graph()` 生成全局图，并把拓扑版本、固定引导比例和区域 1 到区域 2 的测试任务装入导引请求。
3. 客户端向两个区域的 `POST /api/v1/guidance` 提交同一运行 ID。区域工作流从本区数据库读取指定版本的路网快照，把路网、测试任务和导引传给 `LocalSimulationSession`。
4. `simulation_engine/delivered_adapter.py` 将数据库拓扑映射为导引版运行时的节点、道路边和跨区连接。仿真会话调用导引版的区域寻路、`RegionalControl` 和 `partition_motion.advance`。
5. 协调器通过事件准备、提交和帧结束接口同步时钟，转发跨区事件。区域 2 接收 UAV 后重新规划本区路径前缀，并继续推进同一仿真步的剩余时间。每个区域分别写出 UAV 帧和道路统计，结果 API 从 CSV 读取。
6. 区域 DT 完成拥堵评估后上报协调器。原工作流在 `acceptable` 后会调用 `dispatch_guidance()` 向运行系统下发导引。该外部接口仍处于 `IntegrationPending`，当前验收以数据库、规划、移交、统计和集体决策为准，保留区域状态 `waiting_guidance_dispatch`。

演示中的 UAV 由客户端提交，区域网络快照来自 PostgreSQL。CSV 离线加载可以校验路网拼图和算法接缝，实库验收使用 `--topology-source docker`。

## 4. 启动与复现

在交付目录 `metropolis36-integration/sim_docker` 内运行。需要 Docker 与 Compose v2。客户端在宿主机执行时需要 Python 与 NumPy，可在已有 Python 环境执行 `python -m pip install numpy`。

先构建区域镜像，再构建使用它作为基础层的协调器镜像。

```powershell
docker compose build region-dt-01
docker compose build simulation-coordinator
```

### 两区快速验收

协调器在原 Compose 中声明了对 35 区的依赖。用 `--no-deps` 启动列出的两个区域及协调器，可重复运行小规模案例。

```powershell
docker compose up -d --no-deps --no-build --wait --wait-timeout 180 region-dt-01 region-dt-02 simulation-coordinator
$runId = "delivery_db_2regions_" + (Get-Date -Format yyyyMMdd_HHmmss)
python scripts/submit_guidance_demo.py --topology-source docker --regions 1 2 --run-id $runId --duration 10 --verify
```

### 35 区拓扑验收

```powershell
docker compose up -d --no-build --wait --wait-timeout 300
$runId = "delivery_db_35regions_" + (Get-Date -Format yyyyMMdd_HHmmss)
python scripts/submit_guidance_demo.py --topology-source docker --run-id $runId --duration 10 --verify
```

首次同时初始化 35 个数据库时，本次 WSL 环境出现 PostgreSQL 数据目录同步和健康检查超时。保留现有卷，再执行同一组 `up --wait` 命令后，36 个容器全部恢复健康。若冷启动磁盘负载较高，可先用两区命令，也可每次向 `up --no-deps --wait` 传入一组区域服务，待该组健康后再启动下一组。

默认 `--coordinator-url` 是验收客户端访问的宿主地址 `http://127.0.0.1:18080`。区域 DT 在服务内部仍使用请求中的 `http://simulation-coordinator:8080` 注册。宿主机无法访问 WSL 的端口映射时，也可将客户端放到同一个 Docker 网络。以下为在 Bash 环境使用默认 Compose 项目名的例子。

```bash
docker run --rm --network sim_docker_default -v "$(pwd):/workspace:ro" -w /workspace --entrypoint python airway-region-dt:dev -B scripts/submit_guidance_demo.py --topology-source docker --region-url-template 'http://region-dt-{region_id:02d}:8080' --coordinator-url http://simulation-coordinator:8080 --run-id "delivery_db_$(date +%Y%m%d_%H%M%S)" --duration 10 --verify
```

仅启动两区时，在上述容器内命令中补充 `--regions 1 2`。自定义 Compose 项目名时，Docker 网络名相应改为 `<项目名>_default`。

### 查看运行结果

```powershell
Invoke-RestMethod "http://127.0.0.1:18080/api/v1/runs/$runId/attempts/0"
Invoke-RestMethod "http://127.0.0.1:18102/api/v1/simulations/$runId/attempts/0"
Invoke-RestMethod "http://127.0.0.1:18102/api/v1/simulation-results/$runId/attempts/0/snapshot?time=10"
```

输出位于 `output/region_01/<run_id>/attempt_000/` 和 `output/region_02/<run_id>/attempt_000/`。其中 `frame_times.csv` 记录帧时钟，`uav_states.csv` 记录 UAV 所属区域及状态，`edge_statistics.csv` 记录道路统计，`edge_statistics_fixed_60s.csv` 在满 60 秒后才开始写完整周期的统计。协调器运行状态保存在内存中，停服后可通过区域输出 CSV 查看历史帧与统计。

本次 WSL 构建中，普通构建网络未能解析 Alpine 软件源，改用宿主网络后按原 Dockerfile 构建成功。遇到相同问题时，可在 WSL 的 Bash 中使用本次通过的构建命令。

```bash
DOCKER_BUILDKIT=0 docker build --network host -f region_image/Dockerfile -t airway-region-dt:dev .
DOCKER_BUILDKIT=0 docker build -f coordinator_image/Dockerfile -t airway-simulation-coordinator:dev .
```
