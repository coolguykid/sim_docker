# 交付版三种寻路方式与三种执行引擎对比

> 日期：2026-11-19  
> 面向对象：航迹规划算法小组、区域 DT 框架开发人员  
> 目的：说明交付源码中的三种 `routing_mode` 与三种 `execution_engine`，明确导引、安全信息和区域 Docker 的适配边界，并解释为什么当前区域 DT 无法原样使用交付版完整运行链。

## 1. 首先区分两个概念

交付源码同时存在 `routing_mode` 和 `execution_engine`，两者不能混为一谈。

- `routing_mode` 决定“由谁规划路径、一次返回多长的路径”。
- `execution_engine` 决定“规划结果如何进行安全认证、如何推进运动、何时处理事件”。

理论上的组合形式如下：

```json
{
  "routing_mode": "centralized_regional",
  "execution_engine": "certified_journey"
}
```

上述配置表示：航迹按区域计算，但安全服务器仍然在起飞前预测并认证完整航程。

源码位置：

- 寻路方式选择：`src/uav_sim/distributed/regional_backend.py`
- 执行引擎选择：`src/uav_sim/simulation/metropolis_runtime.py`
- 区域寻路核心：`src/uav_sim/distributed/route_planning_server.py`
- 连续运动核心：`src/uav_sim/entities/partition_motion.py`

## 2. 三种寻路方式对比

三种合法的 `routing_mode` 为：

```text
centralized_full
centralized_regional
onboard_regional
```

它们在 `RegionalRoutingBackend.MODES` 中定义。

### 2.1 `centralized_full`

#### 处理方式

中央寻路服务器持有完整 `PartitionMaps`，并创建：

```python
PartitionRoutePlanningCore(maps, full_route=True)
```

收到一次请求后，服务器从当前区域开始，反复调用同一个 `RegionalDijkstra`：

```text
区域 A 前缀
  → 到达 A/B 边界
  → 加载区域 B
  → 计算区域 B 前缀
  → ……
  → 最终目的节点
```

最终一次返回完整的 `edge_ids` 和经过的区域序列。

#### 所需地图信息

中央规划器需要：

- 全局 `PartitionSummary`；
- 所有区域的 `RegionMap`；
- 全局 portal/边界关系；
- 精确目的节点 `Destination`；
- 路网版本和导引代价版本。

#### 导引兼容性

寻路层本身支持导引代价。导引矩阵转换成跨区域边惩罚后，`centralized_full` 会在完整路径搜索中使用这些代价。

但整个仿真能否启用导引，还取决于 `execution_engine`。交付源码只允许 `certified_journey` 启用导引。

#### 与区域 Docker 的关系

当前区域 Docker 不适合直接运行该模式：

- 区域 Docker 的业务约束是只规划本区域路径；
- 当前 UAV 进入下一区域后才由下一区域重新规划；
- `centralized_full` 要求一个服务一次掌握所有区域详细图并返回完整路径；
- 这会绕过现有跨区域移交和严格滚动规划。

即使区域 Docker 收到中心 DT 汇总的全局图，也不代表它应该使用全局图规划其他区域的详细路径。

### 2.2 `centralized_regional`

#### 处理方式

中央寻路服务器仍持有 `PartitionMaps`，但创建：

```python
PartitionRoutePlanningCore(maps, full_route=False)
```

每次只返回当前区域的路径前缀：

```text
当前节点
  → 当前区域内部路径
  → 下一个 BOUNDARY/portal
```

如果最终目的节点就在本区域，则路径前缀直接到达目的节点。

UAV 到达下一区域后，再次提交：

```text
start_node_id
region_id
goal_node_id
```

然后计算新区域的路径前缀。

#### 所需地图信息

单次规划至少需要：

- 当前区域的 `RegionMap`；
- 全局 `PartitionSummary`；
- 当前区域可以到达的 portal；
- 精确最终目的节点描述；
- 路网版本；
- 导引代价版本。

这里的“全局摘要”不是所有区域的详细 lane 数据，而是区域连接关系、portal 摘要、目的节点方向和代价等规划信息。

#### 导引兼容性

寻路层支持导引代价。固定矩阵 P 可转换为当前区域各出口边的附加代价，区域 Dijkstra 根据：

```text
原始通行时间 + 导引附加代价
```

选择当前区域出口。

但交付源码完整运行链仍要求：

```text
启用导引 → execution_engine 必须为 certified_journey
```

#### 与区域 Docker 的关系

这是最符合当前区域 DT 路径所有权的寻路方式：

- 区域只规划本区域；
- 到达共享边界节点后产生移交事件；
- 目标区域收到 UAV 后重新规划；
- 可以使用固定导引 P 调整出口选择。

当前 Docker 接入采用的核心思想就是 `centralized_regional`，但增加了数据库路网适配、共享节点 portal、HTTP 移交和独立区域会话。

需要强调：交付源码中的 `centralized_regional` 只表示“区域级寻路”，并不表示“区域级独立推进”。源码原始运行时仍然在一个 `MetropolisSession` 中保存全部 UAV。

### 2.3 `onboard_regional`

#### 处理方式

路径仍按当前区域计算，但规划请求被分配给 Ray UAV routing actor/group。

中央服务保存完整 `PartitionMaps`，向 worker 发送：

- `PartitionSummary`；
- 当前请求涉及的 `RegionMap`；
- 目的节点描述；
- 规划上下文和版本号。

worker 不持有完整世界详细图，只在需要时加载当前区域地图。

#### 需要注意的所有权

源码中的 worker 是按 UAV ID 分组：

```python
worker_index = uav_id % worker_count
```

它不是“一个区域对应一个 worker”，也不是当前的“一个区域对应一个 Docker”。同一个 worker 可以先后加载多个区域。

#### 导引兼容性

寻路层可以接收带 `cost_revision` 的摘要、区域图和目的节点，因此理论上可以使用导引边代价。

但完整运行链仍受执行引擎限制：交付源码只允许 `certified_journey` 启用导引。

#### 与区域 Docker 的关系

概念上它符合“规划者只看到当前区域图”，但源码实现不能直接作为区域 Docker 服务使用：

- 通信依赖 Ray object reference 和 actor RPC；
- actor 按 UAV 分组，而不是按区域部署；
- actor 只负责寻路，不负责区域运动推进；
- 全局安全控制仍位于一个中央 `MetropolisSession`；
- 没有 Docker 间 UAV 所有权移交协议。

如果要在区域 Docker 使用，需要把 Ray actor 接口改造成稳定的 HTTP/gRPC/进程内函数接口，并按区域服务的生命周期重新定义地图加载和状态所有权。

### 2.4 三种寻路方式汇总

| 对比项 | `centralized_full` | `centralized_regional` | `onboard_regional` |
|---|---|---|---|
| 一次返回路径 | 完整源到目的路径 | 当前区域前缀 | 当前区域前缀 |
| 规划详细图持有者 | 中央服务器 | 中央服务器 | 中央保存，worker按需接收本区图 |
| 规划执行者 | 中央进程 | 中央进程 | Ray UAV routing actor |
| 到边界后是否重新规划 | 不需要 | 需要 | 需要 |
| 是否天然等于区域独立推进 | 否 | 否 | 否 |
| 寻路层能否使用导引代价 | 能 | 能 | 能 |
| 是否符合当前区域路径所有权 | 不符合 | 最符合 | 概念接近，但实现不匹配 |
| 当前区域 Docker 能否原样运行 | 不能 | 需要适配后可以 | 不能 |

## 3. 三种执行引擎对比

三种合法的 `execution_engine` 为：

```text
per_step
certified_prefix
certified_journey
```

### 3.1 `per_step`

#### 推进方式

每个固定仿真步长，把所有活动 UAV 和本步候选起飞 UAV 放入同一个控制器：

```text
收集全局 UAV 当前状态
  → RegionalControl.compute(..., dt)
  → 为每架 UAV 生成当前步运动和完整制动延续
  → 对所有候选轨迹进行连续三维安全审计
  → 冲突时调整加速度/制动
  → 所有 UAV 原子提交到 t + dt
```

#### 全局安全信息的形式

其全局安全信息不是一张数据库表，而是同一进程中的对象集合：

```text
MetropolisSession.active
  ├─ 所有区域 UAV 的 RoadState
  ├─ 当前 edge/route/progress
  ├─ 速度、加速度和三维位置
  └─ 区域编号

RegionalControl 临时预测
  ├─ 每架 UAV 的 PreparedMotion
  ├─ 当前 dt 的 TrajectoryPiece
  ├─ 制动延续轨迹
  └─ 每架 UAV 的安全间距
```

所有区域 UAV 必须在同一次 `RegionalControl.compute()` 中参与联合检查。

#### 是否接入导引

不能。只要：

```python
guidance.enabled == True
```

或者：

```python
guidance.evaluate == True
```

且 `execution_engine != "certified_journey"`，构造 `MetropolisSession` 时就会直接抛出异常。

这属于交付源码的实现限制。

#### 区域 Docker 能否获得这些安全信息

当前不能。

每个区域 Docker 只拥有：

- 本区域路网；
- 本区域 UAV 快照和当前仿真状态；
- 本次导引 P；
- 收到的跨区 UAV 事件。

它不拥有其他 34 个区域全部 UAV 的实时 `RoadState` 和本步候选轨迹。协调器也不会收集和广播完整 UAV 帧。

因此，把 `RegionalControl` 分别放入每个区域 Docker 后，已经不再等价于源码的 `per_step`：源码是全局联合避碰，而 Docker 中变成了区域内部避碰。

### 3.2 `certified_prefix`

#### 推进方式

每次只构造并认证一个安全路径前缀：

```text
当前状态
  → 当前区域路径
  → 下一个 BOUNDARY
```

前缀被转换为解析的连续轨迹，然后提交到全局 `PrefixReservations`。

预留通过后，事件引擎按精确时间执行；前缀结束后再规划和认证下一段。

#### 全局安全信息的形式

安全状态保存在单个内存对象 `PrefixReservations` 中。其核心记录为 `ReservedPhase`，包含：

```text
record_id
uav_id
t0 / t1
三维起点
TrajectoryPiece
安全距离 threshold
轨迹扫掠空间 lower / upper
类型 MOTION / WAIT / HOLD
```

此外还包含：

- 空间网格索引 `_cells`；
- UAV 到预留记录的索引 `_by_uid`；
- 无限期边界/终点占用；
- 等待和重试状态；
- 已预留轨迹的结束时间。

这张预留表覆盖所有区域、所有已经认证的 UAV 前缀。

#### 冲突处理

申请前缀发生冲突时：

1. 尝试推迟前缀开始时间；
2. 尝试缩短前缀并停在区域内部；
3. 保留 UAV 当前静止占用；
4. 等待阻塞轨迹释放后重试；
5. 到区域边界后建立 `HOLD`，直到下一前缀预留成功。

#### 是否接入导引

交付源码中不能。构造 `MetropolisSession` 时会被前述条件直接拒绝。

从算法上并非绝对不能接入。如果外部导引 P 在一次推演中固定，可以让每一次区域前缀规划使用同一个 `guidance_revision`，但交付源码尚未实现证书与外部 P 版本的一致性管理。

#### 区域 Docker 能否获得这些安全信息

当前不能。

各区域 Docker 没有共享 Python 内存，也没有共享 `PrefixReservations`。当前协调器只保存：

- 区域注册信息；
- 当前逻辑时间；
- prepare/commit 事件屏障；
- 跨区事件；
- 移交数量和时序。

它没有保存 `ReservedPhase`、空间索引、边界 HOLD 和安全证书。

所以当前 Docker 虽然已经实现严格事件时间和剩余时间推进，但尚未获得 `certified_prefix` 的跨区域安全语义。

### 3.3 `certified_journey`

#### 推进方式

UAV 起飞前，中央安全服务器预测并认证完整航程：

```text
起点
  → 区域 A
  → A/B 边界
  → 区域 B
  → ……
  → 最终目的节点
```

完整路径被转换成连续轨迹，并一次性放入全局时空预留表。只有整个航程安全时，UAV 才能起飞。

#### 全局安全信息的形式

它比 `certified_prefix` 需要更多全局状态：

1. `JourneyRoutes.reference`
   - 持有全局 `PartitionMaps`；
   - 预测完整参考路径；
   - 保存区域边界后的参考路径。

2. 完整 `TrajectoryProfile` / `_CompositeJourney`
   - 所有区域内的连续加减速轨迹；
   - 精确 `REGION` 事件时间；
   - 完整到达时间和最终状态。

3. 全局 `PrefixReservations`
   - 保存完整航程各运动阶段的时空预留；
   - 与其他 UAV 的完整航程联合检查。

4. `mission_cost_maps`
   - 保存该 UAV 使用的导引代价版本；
   - 区域边界重新规划时继续使用相同代价版本。

#### 边界处理

默认：

```python
stop_at_region_boundaries = True
```

UAV 在边界减速到 0，触发 `REGION` 事件，区域规划器重新计算本区路径，然后与中央安全参考路径比较。

如果区域规划结果与参考路径不同，源码抛出 `ReferenceMismatch`，不会直接采用新路径继续运行。

#### 是否接入导引

能，并且是交付源码唯一允许导引的引擎。

源码导引链为：

```text
当前仿真 UAV 分布
  → GuidanceModel 计算矩阵 P
  → P 转换为跨区域边惩罚
  → 生成带 cost_revision 的 PartitionMaps
  → 规划完整参考航程
  → 认证完整连续轨迹
```

需要注意，交付版 P 是仿真内部计算得到的 `(region, layer) × (region, layer)` 矩阵，不是直接接收中心 DT 下发的外部 P。

#### 区域 Docker 能否获得这些安全信息

当前不能。

区域 Docker 即使获得中心 DT 汇总的全局路网和外部 P，也仍然缺少：

- 所有区域 UAV 的当前状态；
- 其他 UAV 已认证的完整未来轨迹；
- 全局 `PrefixReservations`；
- 全局参考路径和 `JourneyRoutes` 状态；
- 所有区域的实时详细路网；
- 统一的中央安全控制器。

更重要的是，当前业务要求“进入下一区域后才由下一区域规划”，而 `certified_journey` 在起飞前已经预测了所有区域的参考路径。两者业务语义并不一致。

### 3.4 三种执行引擎汇总

| 对比项 | `per_step` | `certified_prefix` | `certified_journey` |
|---|---|---|---|
| 时间推进 | 固定步长 | 精确事件＋固定输出帧 | 精确事件＋固定输出帧 |
| 安全范围 | 当前步＋制动延续 | 当前区域/短路径前缀 | 完整航程 |
| 全局安全信息 | 全局 UAV 当前状态和本步候选轨迹 | 全局 `ReservedPhase` 预留表 | 完整参考路径＋完整轨迹＋全局预留表 |
| 冲突处理 | 调加速度、制动、推迟起飞 | 延迟、缩短前缀、HOLD、重试 | 主要推迟完整航程起飞时间 |
| 到边界后重新规划 | 可在步内调用 | 是 | 是，但必须匹配中央参考路径 |
| 交付源码是否允许导引 | 否 | 否 | 是 |
| 当前区域 Docker 是否拥有所需全局安全信息 | 否 | 否 | 否 |
| 与严格滚动区域规划的匹配程度 | 较低 | 最高 | 较低 |
| 能否原样接入当前 Docker | 不能 | 不能 | 不能 |

## 4. “全局路网”不等于“全局安全信息”

这是当前讨论中最容易混淆的地方。

区域 Docker 可以获得中心 DT 汇总的全局路网，用于：

- 了解区域连接关系；
- 获取目的区域方向；
- 构造 `PartitionSummary`；
- 判断可能的 portal；
- 应用导引 P。

但全局安全信息是随仿真时间不断变化的：

```text
其他区域 UAV 的当前状态
其他 UAV 未来连续轨迹
安全间距
时空预留
边界 HOLD
等待和重试依赖
证书版本
```

仅有全局路网和 P，无法替代上述信息。

## 5. 当前区域 Docker 已经具备和缺少的内容

### 5.1 已经具备

- 每个区域独立数据库和区域路网；
- 数据库路网到交付版 `RoadNode/RoadEdge` 的适配；
- 外部固定导引 P 到边代价的适配；
- `centralized_regional` 区域路径前缀；
- 交付版 `RegionalControl` 和 `partition_motion.advance`；
- 共享节点 portal 移交事件；
- HTTP 长连接；
- 严格事件 prepare/commit 屏障；
- 精确 `crossing_time`；
- 同一仿真步剩余时间推进；
- 区域独立 CSV 帧和区域统计。

### 5.2 仍然缺少

- 跨区域安全准入；
- portal 等待区/HOLD；
- 目标区域对入境轨迹的预检查；
- 分布式 `PrefixReservations` 或等价协议；
- 安全证书 token 和版本管理；
- 目标区域拒绝时源区域的物理减速/停车轨迹；
- 路网调整和导引版本变化后的证书失效处理。

严格事件协调解决的是“时间和所有权正确性”，尚未解决“跨区域联合安全正确性”。

## 6. 当前不能原样使用交付版的原因

### 6.1 源码运行形态不同

交付源码把所有区域 UAV 保存于同一个 `MetropolisSession`，区域变化主要表现为同一 UAV 对象的 `region_id` 变化。

当前系统则是：

```text
A 区域容器删除 UAV
  → 协调器转发移交事件
  → B 区域容器创建 UAV
```

交付源码没有实现这种跨进程状态所有权转移。

### 6.2 全局安全状态没有服务接口

`RegionalControl`、`PrefixReservations`、`JourneyRoutes` 都是 Python 内存对象，没有定义：

- HTTP/gRPC 接口；
- 可持久化安全证书；
- 多区域并发提交协议；
- 跨容器原子更新协议。

### 6.3 导引来源不同

交付版通过仿真内部 `GuidanceModel` 计算 P；当前区域 DT 接收中心 DT 下发的外部 P。

需要一个明确的外部导引接口，而不能依赖交付版内部采样和求解过程。

### 6.4 导引与引擎被强绑定

源码强制：

```text
启用或评估导引 → certified_journey
```

当前系统需要：

```text
外部固定 P
  ＋ 区域滚动规划
  ＋ 跨区域安全准入
```

该组合在交付源码中不存在。

### 6.5 `certified_journey` 与业务目标冲突

它要求起飞前预测完整参考路径，而当前要求进入下一区域后才规划下一区域路径。

即使区域边界仍调用区域规划器，其结果也只能与提前生成的参考路径一致，否则仿真失败。这不是真正自由的滚动区域规划。

## 7. 建议的适配目标

建议不要直接选择三个引擎中的某一个原样部署，而是形成：

```text
centralized_regional
  ＋ 外部固定导引 P
  ＋ certified_prefix 的区域前缀思想
  ＋ 分布式入境安全准入
```

可以暂称：

```text
distributed_certified_prefix
```

其流程建议为：

```text
A 区域规划到 portal 的路径前缀
  → 构造连续运动候选轨迹
  → 预测 crossing_time 和入口状态
  → 向 B 区域申请入境预留
  → B 使用本区 UAV 已认证轨迹检查
      ├─ 接受：返回 reservation_token 和 entry_time
      └─ 拒绝：返回 retry_time/hold_position
  → A 根据结果继续飞行或在 portal 前安全停车
  → 到 entry_time 后协调器执行原子移交
  → B 使用同一个 token 接收并开始本区推进
```

协调器只负责：

- 请求和响应转发；
- 全局逻辑时间排序；
- prepare/commit 屏障；
- 原子移交；
- 超时和重复事件控制。

是否允许进入、采用什么轨迹，仍由目标区域仿真安全模块决定。

## 9. 建议结论

1. 当前路径规划应继续以 `centralized_regional` 为基础。
2. 不建议把 `centralized_full` 作为区域 Docker 的实际飞行路径规划方式。
3. `onboard_regional` 的区域地图可见性思想可以参考，但 Ray/UAV 分组实现不能直接使用。
4. 当前不能直接使用 `per_step`，因为区域 Docker 缺少全局 UAV 候选轨迹。
5. 当前不能直接使用 `certified_prefix`，因为区域 Docker 不共享全局时空预留表。
6. 当前不能直接使用 `certified_journey`，因为它需要完整全局安全预测，并与严格滚动规划冲突。
7. 导引 P 应作为一次推演的外部固定输入，规划和安全证书都必须携带 `guidance_revision`。
8. 最合适的方向是“区域前缀＋目标区域预准入＋portal HOLD＋事件原子移交”。
